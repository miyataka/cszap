### 講評

- **強み**: Q4（アクセス権 rwx）が最も高得点。所有者/グループ/その他の3区分、r/w/xの基本的な意味、ディレクトリでの `x`（`cd` を許可）まで正確に書けている。
- **弱み**: Q2（inode の中身）が未回答。Q1 はシステムコールの列挙で `open`/`read`/`write`/`seek` は正しいが、対になるはずの `close` が抜け、基本的なファイル操作システムコールとしては該当しない `NOTIFY` を混ぜてしまった。Q7 は「特徴を教えてください」という設問後半を読み落とし、ファイルシステム名の列挙だけで終わっている——設問文を最後まで読む練習が要る。
- **伸びしろ**: Q3（シンボリック/ハードリンク）・Q8（空き領域管理）はどちらも核心の分類（filepath vs inode、空きブロックの追跡方式が複数ある）は掴めているが、**帰結や具体的な仕組みまで踏み込めば満点圏**——Q3 なら「リンク先が消えたときの挙動の違い」、Q8 なら「ビットテーブルは1ブロック1ビットで管理する」という具体像。Q4 も「ディレクトリの `w`」を「ファイルの書き込み」とだけ書いており、**エントリの削除・リネームまで含む**という後半が抜けている——満点まであと一歩。

??? question "Q1. ファイルを操作する system call を多く並べて欲しい。　【採点 0.5 / 1.0】"

    **本人の回答**

    > READ
    > WRITE
    > OPEN
    > SEEK
    > NOTIFY

    **模範解答**

    [OS-Files §1](OS-Files.md#file-concept) の基本操作セット: `create` / `open` / `read` / `write` / `seek`（lseek、読み書き位置の移動） / `close` / `delete`（unlink） / `truncate`。`open` はファイル記述子を返し、以後の操作はそれを介する。

    **採点 0.5** — `open`/`read`/`write`/`seek` の4つは正しい。しかし対になるはずの **`close` が抜けている**うえ、`create`/`delete`/`truncate` も出ていない。`NOTIFY` は基本的なファイル操作システムコールとしては該当しない（ファイルシステムのイベント監視という別の仕組み `inotify` は存在するが、設問が聞いている「ファイルを操作する」システムコールとは性質が異なる）。

??? question "Q2. inode には何が保存されているか?　【採点 0.0 / 1.0】"

    **本人の回答**

    > （未回答）

    **模範解答**

    [OS-Files §1](OS-Files.md#file-concept) の**メタデータ**の実体が inode: サイズ・作成/更新日時・所有者・アクセス権・**データブロックへのポインタ**（[OS-Files §3](OS-Files.md#allocation-methods) の索引割り当てでいう直接/間接ブロックポインタ）など、「データそのもの」ではなく「データについてのデータ」一式を持つ。ポイントは、**ファイル名は inode に含まれない**こと——名前は別途ディレクトリエントリ（「名前 → inode 番号」の対応表）側が持ち、名前と実体（inode）が分離されている設計になっている。

    **採点 0.0** — 未回答。

??? question "Q3. シンボリックリンク・ハードリンクの違いは?　【採点 0.7 / 1.0】"

    **本人の回答**

    > シンボリックリンクはfilepathで指定する
    > ハードリンク inodeで指定する

    **模範解答**

    [OS-Files §4](OS-Files.md#directory-structures) の通り、**ハードリンク**は「同じ inode を指す複数の名前」——実体（データブロック）は1つで、名前だけ増える。**シンボリックリンク**は「パス文字列への間接参照」を持つ、それ自体が独立した小さなファイル。この違いは [OS-Advanced-Files §4](OS-Advanced-Files.md#naming-search-backup) の言う通り**ファイル本体の削除タイミング（参照カウント）に現れる**——ハードリンクは元ファイルを消してもリンク先経由で実体が生き残る（inode の参照カウントが0になって初めて解放）が、シンボリックリンクは指し先を消すと**ダングリング（壊れたリンク）**になる。また、ハードリンクは同じファイルシステム内の inode しか指せないのに対し、シンボリックリンクは別ファイルシステム・存在しないパスも指せる。

    **採点 0.7** — 核心（filepath 経由の間接参照 vs inode への直接参照）は正確。ただし**帰結（削除時の挙動の違い、リンクを跨げる範囲の違い）への言及がなく**、そこまで書ければ満点。

??? question "Q4. ファイル・ディレクトリの各アクセス権 r, w, x は何を意味しているか?　【採点 0.9 / 1.0】"

    **本人の回答**

    > 自分自身，自分が所属するグループ，それ以外，の権限を表している
    > rは読み取りを許可している
    > wは書き込みを，xは実行を許可している
    > ディレクトリの場合，rは読み取りを，wはファイルの書き込みを，xはそのディレクトリへ入ること(`cd`)を許可している

    **模範解答**

    [OS-Files §2](OS-Files.md#mount-access-sharing) の ACL 的モデル: Unix の `rwxr-xr--` は**所有者/グループ/その他**の3区分 × **読み/書き/実行**。通常ファイルでは `r`=読み取り、`w`=書き込み、`x`=実行。**ディレクトリ**では意味が変わり、`r`=エントリ一覧の読み取り、`w`=エントリの**追加・削除**（ファイルの作成・削除・リネーム）、`x`=そのディレクトリへ**入る**（`cd`、あるいは中のファイルへパスで直接アクセスする）ことの許可。

    **採点 0.9** — 3区分の構造、r/w/x それぞれの意味、ディレクトリでの `x` の意味（`cd` の許可）は正確。ただしディレクトリの `w` を「ファイルの書き込み」とだけ書いており、**エントリの削除・リネームまで含む**という後半が抜けている——ファイルの中身を書き換える権限（そのファイル自体の `w`）と、ディレクトリ内のエントリ構成を変える権限（ディレクトリの `w`）は別物である点に、もう一歩踏み込めれば満点。

??? question "Q7. 知っているファイルシステムをできるだけ多く並べ、特徴を教えてください。　【採点 0.4 / 1.0】"

    **本人の回答**

    > APFS，ZFS，ext3, ext4, FAT16

    **模範解答**

    列挙自体は妥当な例: **ext3/ext4**（Linux標準、ext4はジャーナリング対応）、**APFS**（macOS、コピーオンライト・スナップショット対応）、**ZFS**（コピーオンライト・チェックサムによる自己修復・スナップショットに強い）、**FAT16/FAT32**（単純だがジャーナリングなし・4GB超のファイル非対応、組み込み/USBメモリ向け）、**NTFS**（Windows標準、ジャーナリング対応）。[OS-Advanced-Files §3](OS-Advanced-Files.md#special-purpose) にある `procfs`/`tmpfs` のような特殊用途ファイルシステムまで挙げられると加点。

    **採点 0.4** — 実在する5つのファイルシステムを正確に列挙できている点は良い。しかし設問は「**特徴を教えてください**」まで求めており、そこに一切答えていない——列挙だけでは設問の半分にしか応えていない。

??? question "Q8. ファイルシステム上でディスクの空き領域はどう管理されているか? (いくつもやり方がある)　【採点 0.6 / 1.0】"

    **本人の回答**

    > ある程度のサイズのブロックとみなし，ブロック番号で空きを管理する方法がある
    > リンクトリストで管理していく方法がある

    **模範解答**

    [OS-Files §5](OS-Files.md#free-space-management) の2方式: **ビットテーブル（ビットベクトル）**——全ブロックに対応する**1ビットずつ**のビット列で空き/使用中を表す。連続した空き領域を走査で見つけやすいが、テーブル自体のサイズがディスク容量に比例する。**リンク方式**——空きブロック同士を連結割り当てと同じ要領で鎖につなぐ。専用テーブルは不要だが、ランダムアクセスができず連続空き領域を探しにくい。どちらを選ぶかは [OS-Files §3](OS-Files.md#allocation-methods) の割り当て方式（連続割り当て中心ならビットテーブル、連結・索引割り当て中心ならリンク方式でも困りにくい）と表裏一体。

    **採点 0.6** — 「複数の追跡方式がある」という骨格と、**リンクリスト方式**は正確。ただし前半の「ブロック番号で空きを管理する」は**ビットテーブル（1ブロック1ビット）の具体的な仕組みとしては不正確**——グループ化方式（空きブロック番号をまとめて記録する、という別の折衷手法）に近い説明になっている。
