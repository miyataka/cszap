## 2026-07-28 出題分（レクチャー後の再テスト：ポリシー/メカニズム分離・KPTI）

!!! abstract "総合スコア"
    **1.6 / 2 ≒ 80 点 / 100**（辛口基準・[前回](#2026-07-27-os-protection-os-process-os-memory-12-q14)は 1.5/4 ≒ 38点 → 出題範囲を弱点2問に絞った再テストで大きく改善）

    | 評価帯 | 問数 | 該当 |
    |---|---|---|
    | 満点（1.0） | 1 | T1 |
    | 半分（0.6） | 1 | T2 |

### 講評

- **克服**: T1（ポリシー/メカニズム）は前回の未回答(0.0)から満点(1.0)へ。定義を完全に言い切れている。
- **改善したが残る誤概念**: T2（KPTI）は前回の「投機実行そのものをoffにする」という誤りは訂正されたが、新たに「カーネル/ユーザーのpage-tableがTLBに同時に乗らないようにする」という**原因と結果の取り違え**が発生。KPTIの本体は**ページテーブル構造そのものの分離**であり、「TLBが同時に乗らない」はその**結果として生じる性能コスト**の説明になっている。原因（ページテーブル分離）と代償（TLBが冷えて遅くなる）を意識して区別すると次は満点。

??? question "T1. OSにおける「メカニズム」の役割を一言で説明してください。　【採点 1.0 / 1.0】"

    **本人の回答**

    > 「どうやって」実現するのかの部分

    **模範解答**

    メカニズム＝「どうやってやるか」の仕組み・実装。ポリシー（何を許すか）とは意図的に分離される。

    **採点 1.0** — 満点。定義そのものを正確に言い切れている。前回(Q1, 0.0・未回答)から完全に克服。

??? question "T2. KPTIは何を分離することで、Meltdown/Spectreの漏洩経路を塞いでいますか？　【採点 0.6 / 1.0】"

    **本人の回答**

    > カーネルモードでのpage-tableとユーザーモードのpage-tableが同時にキャッシュ（TLB）に乗らないようにした．

    **模範解答**

    KPTIの本体は**ページテーブルの構造分離**：カーネル空間のマッピングをユーザー側ページテーブルからほぼ完全に除去する。これにより、ユーザーモードで投機的に実行されても辿る先にカーネルメモリの実体がそもそも存在しない。コンテキストスイッチのたびにTLBが冷えて遅くなるのは、この構造分離の**結果として生じる代償**（原因ではない）。

    **採点 0.6** — 「カーネル/ユーザーのページテーブルを分ける」という方向性は正しい。ただし**「TLBに同時に乗らないこと」を主機構として説明**しており、これは原因（ページテーブル分離）と結果（TLBが冷えるコスト）の取り違え。前回(Q3, 0.3・「投機実行をoffにする」という事実誤認)からは改善。

## 2026-07-27 出題分（OS-Protection / OS-Process / OS-Memory レベル判定クイズ 全12問中 Q1–4）

    |---|---|---|

    | 半分（0.5） | 1 | Q4 |
    | 低（0.3） | 1 | Q3 |
    | ゼロ（0.0） | 1 | Q1 |

### 講評

- **強み**: Q2（ACL vs ケイパビリティ）は「資源側で持つか主体側で持つか」という核心を正確に捉えている。
- **弱み**: Q1（ポリシー／メカニズム分離）が完全な未回答。3ユニット中もっとも手薄なのが Protection ユニット全体。
- **要注意の誤概念**: Q3 で「KPTI は投機実行そのものをオフにする」という誤解が見られた。KPTI の実体は**ページテーブル分離**（カーネル空間をユーザ側ページテーブルからほぼ外す）であり、投機実行自体は止めていない。ここは事実誤認として最優先で修正したい。
- **次の一手**: Q1・Q4 は「具体例を1つ挙げる」練習をすると伸びる（LSM/SELinux、ASLR/NX/サンドボックスなど本文中の具体例を自分の言葉で言い直す）。

??? question "Q1. OSにおける「ポリシー」と「メカニズム」の違いを一言で説明し、具体例を1つ挙げよ。　【採点 0.0 / 1.0】"

    **本人の回答**

    > わからん

    **模範解答**

    **メカニズム**＝「どうやってやるか」の仕組み（例：ページ保護ビット、権限チェックのフック）。**ポリシー**＝「何を許すか」の決定（例：このユーザはこのファイルを読める）。分離しておくと**仕組みを作り直さずに方針だけ変えられる**。例：Linux の LSM（Linux Security Modules）はフック（メカニズム）を提供し、SELinux や AppArmor が各々のポリシーを載せる。

    **採点 0.0** — 未回答。[OS-Protection §5](OS-Protection.md#policy-mechanism) を読み直すこと。

??? question "Q2. アクセス制御の実装方式である「ACL」と「ケイパビリティ」の違いを説明せよ。　【採点 0.7 / 1.0】"

    **本人の回答**

    > アクセスコントロールリストはallow/deny list，リソース側が許可できる主体がなにかを明示する．ケイパビリティは主体側がなにができるのかを保持する

    **模範解答**

    概念モデルは**アクセス制御行列**（主体 × 資源 → 権限）。**ACL**は行列を**資源側**（列）で持つ（例：Unix の `rwxr-xr--`、ファイルごとの ACL）。**ケイパビリティ**は行列を**主体側**（行）で持つ、「持っていること自体が権限」のトークン（例：ファイルディスクリプタ）。

    **採点 0.7** — 「資源側 vs 主体側」という核心を正確に捉えている。具体例（Unix の `rwx` / ファイルディスクリプタなど）を添えれば満点。

??? question "Q3. Meltdown/Spectre はCPUのどの機構の副作用として情報漏洩を引き起こしたか。また緩和策KPTIは何を代償にするか。　【採点 0.3 / 1.0】"

    **本人の回答**

    > 投機実行．投機実行性能をoffにして性能を犠牲にする

    **模範解答**

    **投機実行**の脆弱性：投機的に実行された（本来届かないはずの）アクセスの痕跡が**キャッシュに残り**、タイミング測定で読み取れる。緩和策 **KPTI**（カーネル空間をユーザのページテーブルからほぼ外す＝**ページテーブル分離**）や、切替時のキャッシュ・分岐予測のフラッシュにより、コンテキストスイッチとシステムコールが**恒常的に高コスト化**する（セキュリティと性能のトレードオフ）。

    **採点 0.3** — 機構名（投機実行）は正しいが、**「キャッシュに痕跡が残りタイミング測定で読める」という漏洩経路に未言及**。さらに「KPTIは投機実行性能をoffにする」は**事実誤認**——KPTI の実体はページテーブル分離で、投機実行自体は止めていない。

??? question "Q4. 新しいOSサービスを設計する際、「最小権限の原則」と「多層防御」をどう適用するか、具体例を1つ挙げて説明せよ。　【採点 0.5 / 1.0】"

    **本人の回答**

    > 権限を必要最小限にする．複数の仕組みで多層防御を作る．

    **模範解答**

    **最小権限の原則**＝各プロセス・ユーザに必要最小限の権限だけ与え、破られたときの被害を限定する。**多層防御**＝ASLR（アドレス配置のランダム化）・NX ビット（データ領域を実行不可に）・サンドボックスを重ね、1枚破られても次の層で止める。例：Webブラウザは各タブを別プロセス（最小権限・分離）にしつつ、ASLR/NX/サンドボックスを併用する。

    **採点 0.5** — 2つの概念自体は正確に言い直せている。設問が要求する**具体例が無い**ため減点。
