!!! info "使い方"

    - 採点は**辛口基準**（本質＋理由付け＋正しい用語が揃って満点。簡潔すぎ・論拠が弱い・用語が出ないものは減点。誤答／未回答／書きかけは 0〜0.3）。

## 2026-07-28 出題分（レクチャー後の再テスト：TLB・スラッシング・COW統合問題）

!!! abstract "総合スコア"
    **2.1 / 3 ≒ 70 点 / 100**（辛口基準・[前回](#2026-07-27-os-protection-os-process-os-memory-12-q912)は 1.1/4 ≒ 28点 → 3ユニット中もっとも低かったユニットが最大の伸び幅）

    | 評価帯 | 問数 | 該当 |
    |---|---|---|
    | 満点（1.0） | 1 | T4 |
    | 半分（0.5〜0.6） | 2 | T6, T7 |

### 講評

- **完全に克服**: T4（ページテーブル vs TLB）は前回の弱点（TLB固有の役割に届かない, 0.3）を完全克服。「どこに」「何のために」を書き分けて満点。
- **結論は合うがメカニズムがズレる共通パターン**: T6（スラッシング）は「進まなくなる」という結論は正しいが、ボトルネックを「コンテキストスイッチ」と誤って説明——実際はページイン/アウト（ディスクI/O）の連発が主犯。T7（COWと同型の統合問題を動的リンクに応用）も「コード実行の脆弱性になる」という結論は妥当だが、**タイミングのスキという機構そのものへの言及がない**。
- **伸びしろ**: 前回2問とも未回答(0.0)だったT6・T7が、結論だけでも言えるようになったのは前進。次は「**なぜそのタイミングで**問題が起きるか」という機構の解像度を上げる練習（本文の§4・§8を読み直し、時系列で図に起こすと効果的）。

**T4.** ページテーブルとTLBの違いを、「どこに」「何のために」あるかという観点で説明してください。

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > ページテーブルはメモリ上に，virtual-memoryとphysical-memoryの変換のためにある．TLBはCPU/MMU内部にpage-tableのキャッシュを保持し，アドレス変換を高速化する

    **模範解答**

    変換表（ページテーブル）を毎回メモリから引くと遅すぎるので、MMU が変換結果をキャッシュしておく仕組みが TLB。ページテーブルは主記憶上にありアドレス変換そのものを担う。TLBは CPU/MMU内部の小容量キャッシュで、直近使った変換結果を保持し高速化する。

    **採点 1.0 / 1.0** — 満点。「どこに」（メモリ上 vs CPU内部）「何のために」（変換そのもの vs 高速化のキャッシュ）を正確に書き分けている。前回(Q9, 0.3)から完全に克服。

**T6.** 4GBのメモリを積んだマシンで、合計10GB分のワーキングセットを持つプロセス群を同時に動かしたとき、何が起きますか？

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > スラッシングが発生し，コンテキストスイッチでどのプロセスの処理も進まない，という状況が起きる

    **模範解答**

    ワーキングセットの合計(10GB)が物理メモリ(4GB)を超えるため、フレームの奪い合いで**ページイン/アウト（ディスクI/O）が絶え間なく発生**するスラッシングが起きる。1回のページフォルトはディスクアクセスを伴い、CPU計算に比べて桁違いに遅いため、実質的な計算がほとんど進まなくなる。対策は多重度を下げるかメモリを増やすかしかない。

    **採点 0.6 / 1.0** — 「スラッシングが起きて進まない」という結論は正しい。ただしボトルネックの正体を**「コンテキストスイッチ」と誤って説明**——コンテキストスイッチ自体は軽い操作で主犯ではない。実際はページイン/アウト（ディスクI/O）の連発がボトルネック。前回(Q11, 0.0・未回答)からは前進。

**T7（統合問題）.** もし「共有ライブラリの動的リンク」の実装に、Dirty COWと同様のタイミングのスキがあったとしたら、どんな種類の被害が起こりうると思いますか？（Dirty COWの構造を応用して推測してください）

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > 意図しないコードをリンクしてしまい，任意コード実行の脆弱性につながる

    **模範解答**

    動的リンクも「複数プロセスが同じ物理フレーム（共有ライブラリのテキスト領域）を指す」という共有の仕組みを使っている。もしマッピングの**検証と確定の間にタイミングのスキ**があれば、悪意あるコードを共有フレームに書き込める可能性がある。Dirty COWと違うのは、**被害が1ファイルではなく「そのライブラリを使う全プロセス」に及ぶ**点——共有される物理フレームが1つである以上、そこへの汚染は共有元すべてに波及する。

    **採点 0.5 / 1.0** — 「コード実行の脆弱性になる」という結論の方向性は妥当。ただし**Dirty COWの構造（タイミングのスキを突く機構）への言及がなく**、また「共有フレーム経由で被害が全プロセスに波及する」という規模の洞察も欠けている。前回(Q12, 0.0・未回答)からは前進したが、統合的推論はまだ発展途上。

## 2026-07-27 出題分（OS-Protection / OS-Process / OS-Memory レベル判定クイズ 全12問中 Q9–12）

!!! abstract "総合スコア"
    **1.1 / 4 ≒ 28 点 / 100**（辛口基準・3ユニット中もっとも低得点）

    | 評価帯 | 問数 | 該当 |
    |---|---|---|
    | 良（0.8） | 1 | Q10 |
    | 低（0.3） | 1 | Q9 |
    | ゼロ（0.0） | 2 | Q11, Q12 |

### 講評

- **強み**: Q10（デマンドページング／ページフォルト）は正確。
- **弱み**: Q9（TLB）は「MMU・アドレス変換」全般の説明に終始し、**TLB固有の役割（変換結果のキャッシュによる高速化）に届いていない**。Q11（スラッシング）・Q12（Dirty COWとユニット横断の統合問題）は未回答——特に Q12 は Protection ユニットとの接続を問う統合設問だっただけに、両ユニットとも手薄な今の状態を象徴している。
- **次の一手**: Q9 は「なぜページテーブルを毎回メモリから引かず TLB を使うのか＝速度」という一点を補えば大きく伸びる。Q11・Q12 は本文（OS-Memory §4, §8）を読み直してから再テストするのが効率的。

**Q9.** TLB（Translation Lookaside Buffer）とは何か。なぜ必要か。

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > 仮装メモリと物理メモリのアドレス変換のために必要．プロセスに他のプロセスのメモリを見せないように分離するために必要

    **模範解答**

    変換表（ページテーブル）を**毎回メモリから引くと遅すぎる**ので、MMU が変換結果をキャッシュしておく仕組みが TLB。直近使ったアドレス変換をキャッシュに保持し、ヒットすれば高速に物理アドレスへ変換できる。

    **採点 0.3 / 1.0** — 「アドレス変換」「分離」は MMU 全般の目的としては正しいが、これは**ページテーブル（MMU）そのものの役割**であり、**TLB固有の役割（変換をキャッシュして高速化する）に言及がない**。設問は TLB 固有の存在意義を問うている点に注意。

**Q10.** デマンドページングとページフォルトの関係を説明せよ。

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > デマンドページングは必要になったときにページを取得しにいく．ページフォルトはそのページが必要なときにメモリ上にないこと

    **模範解答**

    **デマンドページング**：ページは触られたときに初めて割り当て・読み込みする。**存在しないページへのアクセスはページフォルト**（例外）となり、OS がそれを処理（ディスクから読み込み・フレーム割り当て）した上でアクセスを再実行する。

    **採点 0.8 / 1.0** — 両者の関係を正確に説明。「例外として処理され、処理後にアクセスを再実行する」という後段まで書ければ満点。

**Q11.** スラッシング（thrashing）が起きるメカニズムと、その対策を説明せよ。

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > （未回答）

    **模範解答**

    全体のフレームが足りず、**ページ入れ替えばかりで仕事が進まない**状態。実行に「いま必要なページ集合」（ワーキングセット）がメモリに収まらないのが原因。対策は**多重度を下げる**（中期スケジューラで実行中プロセス数を減らす）か、**メモリを増やす**しかない。

    **採点 0.0 / 1.0** — 未回答。

**Q12.** Dirty COW脆弱性は何の機構のバグだったか。そして、なぜ「競合状態のバグ」がそのまま「権限昇格」につながったのか。OS-MemoryとOS-Protection両方の内容を結びつけて説明せよ。

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > （未回答）

    **模範解答**

    **コピーオンライト (COW)**（[OS-Memory §8](OS-Memory.md#virtual-memory-services)）——fork 時にページを共有し、書いた瞬間だけ複製する機構——の**競合状態（race condition）**のバグ。COW 処理のタイミングを突くことで、本来読み取り専用のはずのファイルに書き込めてしまった。これは並行性バグ（[OS-Concurrency](OS-Concurrency.md)）が [OS-Protection §3](OS-Protection.md#real-vulnerabilities) の言う「実在OSの重大脆弱性」として現れた例で、メモリ管理の最適化機構（COW）が**そのまま権限昇格の攻撃経路**になった——ユニットをまたいだ理解が問われる典型例。

    **採点 0.0 / 1.0** — 未回答。3ユニットを横断する統合設問であり、今回の未回答の中でも特に復習優先度が高い。
