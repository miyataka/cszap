!!! info "使い方"
    - 設問は常に表示。**「回答・模範解答・採点を開く」をクリックすると本人の回答・模範解答・採点が開く**。再テストのときは開かずに自分で答えてから照合する。
    - 採点は**辛口基準**（本質＋理由付け＋正しい用語が揃って満点。簡潔すぎ・論拠が弱い・用語が出ないものは減点。誤答／未回答／書きかけは 0〜0.3）。

### 講評

**T3.** コンテキストスイッチの際、PCBに保存されている情報のうち、「レジスタ・PC」以外で最低限必要なものを1つ挙げてください。

??? note "回答・模範解答・採点を開く"

    **採点 1.0 / 1.0** — 満点。要求は1つだが3つとも正確に挙げている。前回(Q5, 0.3・PIDのみ)から完全に克服。

**T5.** あるサーバプロセスが、子プロセスと大量の画像データを高頻度でやり取りしたいが、同期のコードは自分では書きたくないとします。どのIPC機構を選ぶべきですか？理由も添えてください。

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > メッセージパッシングを利用するべき．同期の仕組みがカーネルで提供されているから

    **模範解答**

    **メッセージパッシング**（パイプ・ソケット・メッセージキュー）を選ぶ。共有メモリは最速だが同期が仕組みに内蔵されておらず自前実装が要る。メッセージパッシングはカーネル経由の送受信（コピーあり）で**同期が仕組みに内蔵され安全**——「同期を自前で書きたくない」という条件が共有メモリを除外する決め手になる。

    **採点 0.9 / 1.0** — 核心（同期が組み込まれている）を正しく選べている。前回(Q8, 0.0・未回答)から大幅改善。「共有メモリの方が速いが同期は自前」という比較を明示できれば満点。

## 2026-07-27 出題分（OS-Protection / OS-Process / OS-Memory レベル判定クイズ 全12問中 Q5–8）

!!! abstract "総合スコア"
    **2.1 / 4 ≒ 53 点 / 100**（辛口基準・3ユニット中もっとも高得点）

    | 評価帯 | 問数 | 該当 |
    |---|---|---|
    | 良（0.9） | 2 | Q6, Q7 |
    | 低（0.3） | 1 | Q5 |
    | ゼロ（0.0） | 1 | Q8 |

### 講評

- **強み**: Q6（スタック/ヒープ）・Q7（静的/動的リンク）は模範解答にかなり近い水準。トレードオフを理由つきで語れている。
- **弱み**: Q5 は「3つ挙げよ」に対し PID のみ（1/3）。Q8（IPC の使い分け）は未回答——3ユニット中もっとも実務的な設問だっただけに惜しい。
- **次の一手**: Q5 は PCB の構成要素（状態・保存レジスタ・アドレス空間情報・開いているファイル・優先度）を暗記し直すだけで満点圏。Q8 は本文の「使い分け表」（データ量×頻度×方向×同期の要否）を軸に考える練習をするとよい。

**Q5.** PCB（Process Control Block）に含まれる情報を3つ挙げよ。

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > pid

    **模範解答**

    PID・状態（ready/running/waiting等）・保存レジスタ・アドレス空間情報（ページテーブルへのポインタ）・開いているファイル・優先度　など。

    **採点 0.3 / 1.0** — PID は正しいが「3つ」の要求に対し1つのみ。

**Q6.** スタックとヒープでは、メモリの確保・解放コストと寿命がどう違うか説明せよ。

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > スタックは関数呼び出しで自動的に確保され，関数が終了するタイミングで自動的に解放される．ヒープは関数とは独立して確保・解放される．オブジェクトや変数を確保した時に確保される．プログラマ自身がfreeするか，GCで回収されるまで解放されない．

    **模範解答**

    **スタック**は確保・解放がポインタ移動だけで超高速だが、寿命が関数スコープに縛られる（関数リターンで自動解放）。**ヒープ**は寿命が自由だが、確保コストと**断片化**・解放忘れ（リーク）の問題を持つ（明示的に解放するまで生きる）。

    **採点 0.9 / 1.0** — 確保・解放のタイミングと寿命の違いを正確に説明。「断片化」というコスト面の語まで出れば満点。

**Q7.** 静的リンクと動的リンクのトレードオフを説明せよ。

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > 静的リンクは，実行ファイルが大きくなる代わりに実行時にライブラリ読み込みやリロケーションが不要で早い．ライブラリを更新したいときはrebuildが必要．動的リンクは実行ファイルが小さく，ライブラリのバージョン差し替えなどが行いやすい．

    **模範解答**

    **静的リンク**: ライブラリのコードを実行ファイルに埋め込む。単体で動くが、ファイルが大きく、ライブラリ更新には再リンクが要る。**動的リンク**: 実行時（ロード時）に共有ライブラリを割り付けて参照を解決する。同じライブラリのテキスト領域を全プロセスで**物理的に共有**できるためメモリ効率がよく、ライブラリだけ更新できる（セキュリティパッチ）。代償は起動時の解決コストと「入れ替わり」のリスク。

    **採点 0.9 / 1.0** — サイズ・起動速度・更新のしやすさというトレードオフを的確に説明。「複数プロセス間でテキスト領域を物理共有できる」というメモリ効率の観点まで出れば満点。

**Q8.** 「大量データを高頻度でやり取りしたいが、同期は自前で書きたくない」場合、どのIPC機構を選ぶべきか。理由とともに述べよ。

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > （未回答）

    **模範解答**

    **メッセージパッシング**（パイプ・ソケット・メッセージキュー）を選ぶ。共有メモリは最速だが同期が仕組みに内蔵されておらず自前実装が要る。メッセージパッシングはカーネル経由の送受信（コピーあり）で**同期が仕組みに内蔵され安全**——「同期を自前で書きたくない」という条件が共有メモリを除外する決め手になる。

    **採点 0.0 / 1.0** — 未回答。「共有メモリ＝最速だが同期は自前」というトレードオフが設問の核心。
