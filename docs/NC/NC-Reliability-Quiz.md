### 講評

- **強み**: Q11（TCP/UDP の使い分け）・Q13（到達確認）・Q14（順序保存）は、シーケンス番号と ACK の役割を正しく説明できている。
- **弱み**:
    1. **誤り検出の核心語が欠落** — Q12（1パケットの中身が壊れていないか）を「IP パケットのヘッダを確認する」とだけ答えたが、正しくは**チェックサム**による検出。ヘッダを見るだけでは何を確認しているのか説明になっていない。
    2. **層をまたぐ責任の取り違え** — Q15（TCP は確実に届けるか）で「ルータが確率的にパケットロスを起こす」ことをもって「確実とは限らない」と結論づけているが、これは**下位層（IP）の性質**であり、TCP はまさにその不確実な土台の上で ACK・タイムアウト・再送によって**再送可能な限り確実な配送を実現する**プロトコル（[§2](NC-Reliability.md#reliability-principles)）。信頼性が保証しないのは「いつ届くか」（時間保証）である点も踏まえていない。
    3. **3-way handshake が根本的に誤り** — Q18 は正しい順序・名称（SYN → SYN-ACK → ACK）に到達できていない（「ack, syn-ack, start」）。
    4. **未回答2問** — Q17（TCP のペース調整の**具体的な方法**＝ウィンドウ方式・rwnd/cwnd）、Q19（TCP の状態遷移）はいずれも空欄。
- **次の一手**: Q12・Q15 は [§2〜§3](NC-Reliability.md#reliability-principles) の「信頼性の4性質」と「エンドツーエンド原則」を読み直す。Q17・Q18・Q19 はこのユニット最大の弱点（4ユニット中最低スコア）なので、[§4](NC-Reliability.md#flow-control)（スライディングウィンドウ）を最優先で復習し、3-way handshake と TCP 状態遷移は本サイト未収録のため別途補強が必要。

**Q11.** どのような場合に UDP を使いたく、どのような場合に TCP を使いたくなるのか?

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > TCPはパケットの到着順が重要なときだったり，コネクションを確立して，到達確認をとりたいときに用いる
    > UDPはパケットを送信したあとに，到達確認は行わないし，再送も行わないので，おおよそのトラフィックの流れが一方的な1:Nの配信などに向いている

    **模範解答**

    選択の基準は**アプリケーションの要求**（[NC-Applications §3](NC-Applications.md#app-demands)）。**ロスが許されないなら TCP**（ファイル転送・Web・メール）、**遅延が最優先でロスに耐えられるなら UDP**（ライブ音声・映像・DNS の問い合わせ）（[NC-Applications §5](NC-Applications.md#tcp-vs-udp)）。UDP を選ぶことは「信頼性を捨てる」のではなく「**信頼性を自分で設計する**」ことでもある（[§1](NC-Reliability.md#unreliable-delivery)）。

    **採点 0.8 / 1.0** — 順序保証・到達確認の有無という核心の違いを正しく説明。「ロス耐性」という設問の軸（帯域・遅延・ロス耐性）に明示的に触れると満点。

**Q12.** 1パケットのデータの中身が壊れていないことを確認するにはどうするのか?

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > IPパケットのヘッダを確認することでデータが壊れていないことが確認できる

    **模範解答**

    **チェックサム**（UDP はヘッダ＋データ、TCP も同様）や、リンク層の **CRC**（[NC-SingleHop §2](NC-SingleHop.md#framing)）によって誤り検出を行う（[§1](NC-Reliability.md#unreliable-delivery)、[§3-誤り訂正](NC-Reliability.md#error-correction)）。送信側が計算した検査値を付けて送り、受信側が同じ計算をして一致するか確認する、という仕組み。

    **採点 0.3 / 1.0** — 「ヘッダを確認する」だけでは**何を確認しているか**（チェックサムという具体的な検査値の一致）が説明されておらず、核心を外している。

**Q13.** 1パケットが相手に届いているか確認するにはどうしたらよいか?

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > 相手が送り返してきたパケットに，受信した最大シーケンス番号が載っているのでそれでどこまで到達したのかを判別できる

    **模範解答**

    受信側が **ACK（肯定応答）** を送り返し、そこに「ここまで受け取った」というシーケンス番号を載せる（[§3-再送](NC-Reliability.md#retransmission)）。ACK が一定時間来なければタイムアウトとみなして再送する。

    **採点 0.7 / 1.0** — 累積 ACK の仕組み（最大シーケンス番号で到達を判別）を正しく説明。「ACK」という用語そのものと「タイムアウトで再送を判断する」までを明示すれば満点。

**Q14.** データの順序が入れ替わっていないことを確認するにはどうしたらよいか?

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > 受信したパケットにシーケンス番号があるので，それが連続して増加していることを確認すればよい

    **模範解答**

    各データに付けた**シーケンス番号**が連続して増加しているかを受信側で確認する。抜けや逆転があれば、順序が保存されていないと分かる（[§2](NC-Reliability.md#reliability-principles)、[§3-再送](NC-Reliability.md#retransmission)）。

    **採点 0.8 / 1.0** — 正確。シーケンス番号が「重複検出」と「順序復元」の両方に使われる、という2つ目の役割まで言えると満点。

**Q15.** TCP ではデータを確実に受け取れるのか?

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > 確実とは限らない．中継したルーターが確率的にパケットロスを起こすなどは普通に起こりうる

    **模範解答**

    TCP は**無損失・無重複・順序保存・完全性**という4つの性質を保証するよう設計されている（[§2](NC-Reliability.md#reliability-principles)）。ルータでのパケットロスは実際に起きるが、TCP は ACK・タイムアウト・再送によってそれを**回復**するため、接続が維持される限り最終的には確実に届く。ただし TCP が保証するのは「届くこと」であって「**いつ届くか**」（時間・帯域）ではない——応答が数秒かかることもある。

    **採点 0.3 / 1.0** — 「ルータでロスが起きる」こと自体は正しいが、それは**下位層（IP）の性質**であり、TCP はその上で再送によって信頼性を回復するプロトコルである、という関係が逆転している。「確実とは限らない」という結論の根拠が的外れ。

**Q16.** TCPでは、データを送るペースを調整しているが、これはなぜ必要か? UDP での通信では不必要か?

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > 通信経路上のボトルネックとなっているルーターなどの機器の性能に合わせて調整することで，最大スループットがでるようにしている．
    > また，他のトラフィックを妨害しないようにしている

    **模範解答**

    速い送信者が遅い受信者や混雑した網を溢れさせないための**フロー制御**（受信側を守る）と**輻輳制御**（網を守る）の2つが必要（[§4](NC-Reliability.md#flow-control)、[§5](NC-Reliability.md#congestion-control)）。**UDP はこれを一切行わない**——輻輳制御に縛られない代わりに、網に対する責任もアプリ側が負う（[NC-Reliability §1](NC-Reliability.md#unreliable-delivery)）。したがって UDP で「不要」なのではなく、**必要なら自分で実装しなければならない**（QUIC が好例）。

    **採点 0.5 / 1.0** — TCP 側の理由（ボトルネックへの適応、他トラフィックへの配慮＝輻輳制御の目的）は正しい。だが**フロー制御と輻輳制御を区別せず**、また設問後半の「UDP では不必要か」に明示的に答えていない（不要なのではなく責任がアプリに移るだけ、という核心が無い）。

**Q17.** TCPでは、どのようにデータを送るペースを調整しているか?

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > （未回答）

    **模範解答**

    受信側は ACK に**受信ウィンドウ (rwnd)**——あと何バイト受け取れるか——を載せて通知し（フロー制御）、送信側はそれと自分が推測する**輻輳ウィンドウ (cwnd)** の小さい方 `min(rwnd, cwnd)` までしか送らない（輻輳制御）（[§4](NC-Reliability.md#sliding-window)、[§5](NC-Reliability.md#congestion-control)）。`cwnd` はスロースタート（指数的増加）→ 輻輳回避（線形増加）→ 損失検知で減少、という AIMD で調整される（[§6](NC-Reliability.md#tcp-mechanisms)）。

    **採点 0.0 / 1.0** — 未回答。

**Q18.** TCPの 3-way handshake について説明してほしい。

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > ack, syn-ack, start

    **模範解答**

    接続を確立する3段階のやり取り：(1) クライアントが **SYN**（接続要求・初期シーケンス番号）を送る、(2) サーバが **SYN-ACK**（要求への確認＋自分の初期シーケンス番号）を返す、(3) クライアントが **ACK** で応答して確立が完了する。以後、両者は合意した初期シーケンス番号を起点にデータをやり取りする。

    **採点 0.1 / 1.0** — 「syn-ack」という語は出ているが、**順序・名称が両方誤っている**（正は SYN → SYN-ACK → ACK。「start」という段階は存在しない）。この設問は本サイトの NC-Reliability 本文では扱っていない（TCP の内部プロトコルの詳細）ため、別途補強が必要。

**Q19.** TCP の各状態について説明してほしい。

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > （未回答）

    **模範解答**

    代表的な状態遷移：`LISTEN`（サーバが接続待ち）→ `SYN_SENT` / `SYN_RCVD`（handshake 中）→ `ESTABLISHED`（データ送受信可能）→ `FIN_WAIT` / `CLOSE_WAIT`（どちらかが切断を開始）→ `TIME_WAIT`（能動的に閉じた側が、遅延パケットの取りこぼしを防ぐため一定時間待つ）→ `CLOSED`。

    **採点 0.0 / 1.0** — 未回答。この設問も本サイトの NC-Reliability 本文では扱っていない項目のため、別途補強が必要。
