### 講評

- **強み**: Q5 は「デバイスへの保存は保証されない・同期的な呼び出しが要る」という**結論と理由付けの方向性は正しい**。
- **弱み**: Q9（ジャーナリングの利点・欠点）は「利点:」「欠点:」という見出しだけで中身が空——実質未回答。5ユニット横断クイズの中でも最も内容が薄い設問だった。
- **次の一手**: Q5 は「なぜ保証されないか」の機構（write はページキャッシュに書くだけで、実デバイスへの書き戻しはOSが随時・非同期に行う）まで踏み込めば満点。Q9 は本文（[OS-Advanced-Files §5](OS-Advanced-Files.md#journaling)）を読み直し、「write-ahead logging」「fsck 不要」という2語を軸に再構成すると書きやすい。

**Q5.** ファイルを open して write して close した。データはデバイスに必ず保存されているか? されないなら、どうすればよいのか?

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > デバイスへ保存されているとは限らない．
    > FLUSHなど同期的な書き込みをするシステムコールをする必要がある

    **模範解答**

    保証されない。`write` は多くの場合**ページキャッシュ**への書き込みで完了し、実デバイスへの反映（書き戻し）は OS がタイミングを見て非同期に行う。[OS-Advanced-Files §2](OS-Advanced-Files.md#mmap) の言う**ダーティビット**（変更されたページに立つ）が、OS が随時・メモリ圧迫時・あるいは明示的な同期呼び出し（`fsync`/`fdatasync`、mmap 経由なら `msync`）のタイミングでディスクへ書き戻される。**クラッシュ時にはまだ書き戻されていない変更が失われうる**——この耐障害性の問題を軽減する仕組みが [OS-Advanced-Files §5](OS-Advanced-Files.md#journaling) のジャーナリング。

    **採点 0.7 / 1.0** — 「保証されない・同期的な呼び出しが要る」という結論と理由の方向性は正しい。ただし `FLUSH` は正式なシステムコール名ではなく（実際は `fsync`/`fdatasync`/`msync` 等）、**なぜ保証されないか（ページキャッシュに書くだけで実デバイスへの書き戻しは非同期）という機構への言及がない**。

**Q9.** ジャーナリングファイルシステムの利点と欠点は?

??? note "回答・模範解答・採点を開く"

    **本人の回答**

    > 利点:
    > 欠点:

    **模範解答**

    [OS-Advanced-Files §5](OS-Advanced-Files.md#journaling) より。**利点**: 実際の更新の**前に**その内容をジャーナル（ログ領域）へ先に書く（write-ahead logging）ことで、クラッシュ後の起動時に**ジャーナルを読んで未完了の操作をやり直す／巻き戻すだけ**でよく、旧来の全ディスクスキャン（`fsck`）と比べ復旧が桁違いに速くなる。**欠点**: 更新内容をジャーナルとファイル本体の**両方に書く**ため、書き込みが二重になりオーバーヘッドが生じる。ジャーナル領域そのものの記憶域コストもかかる。

    **採点 0.0 / 1.0** — 見出しのみで内容が空。実質未回答。
